# 检测业务多角色与工作流优化说明

本文基于原有检测业务角色与工作流基础，结合企业级应用的权限精细化、流程规范化、管理可落地、风险可管控需求，对角色权限、工作流衔接、管控规则等进行优化，明确后台已落地功能、优化后内容及后续API/App衔接要求，确保角色权责清晰、流程闭环、操作可追溯。

---

## 一、优化核心原则（企业级应用适配）

1. **权责对等**：每个角色的权限严格匹配其岗位职责，避免越权操作，同时确保岗位工作可正常开展，无权限缺失导致的工作卡点；

2. **精细化管控**：拆分模糊权限，补充数据权限、操作权限的分级控制，适配企业“分级管理、层层负责”的管理模式；

3. **流程闭环**：完善环节衔接、退回规则、签字校验，确保案件从发起至签发的全流程可追溯、可管控，避免流程漏洞；

4. **可扩展性**：预留角色、权限、流程的扩展空间，适配未来检测业务新增场景（如多站点、多类型检测）；

5. **易用性**：优化角色界面展示、权限配置入口，降低管理员维护成本，同时贴合各岗位实际操作场景，减少无效操作。

---

## 二、角色优化（系统级Role\.code）

保留原有super\_admin、admin、app\_user（兼容旧数据）、template\_tester角色，优化新增五类检测业务角色的权责定义，补充权限细分、数据范围控制，明确角色互斥与关联规则，适配企业级岗位管控需求。

### 2\.1 优化后角色详情表

|代码|名称|核心职责（优化后）|基础权限（优化后）|数据权限|
|---|---|---|---|---|
|field\_inspector|检测员|1\. 现场检测数据真实填写、现场记录上传（需本人签字确认，不可代签）；2\. 接收现场检测任务分配；3\. 配合校核员完成现场记录复核，修改反馈问题；4\. 仅负责案件首环节（现场填写），不可跳过或越权操作后续环节。|文件库查看（仅本人负责的现场记录）、文件上传（仅限现场记录相关）、案件查看（本人负责的未完成案件）、签字确认（本人操作环节）|仅查看、操作本人被分配的项目及案件，不可查看其他检测员的现场记录|
|site\_reviewer|校核员|1\. 检测员完成现场记录签字上传后，对记录的真实性、完整性、规范性进行校核；2\. 校核通过后签字确认，推进至报告编制环节；3\. 校核不通过时，明确退回原因，退回至检测员环节并跟踪修改；4\. 不可修改现场记录内容，仅可退回修改。|文件库查看（本项目所有现场记录）、校核操作、签字确认、退回操作、案件查看（本项目所有未完成案件）|查看、校核本项目下所有检测员的现场记录，不可查看其他项目的校核数据|
|report\_author|编制人|1\. 依据校核通过的现场记录编制检测报告，确保报告数据与现场记录一致；2\. 编制完成后签字确认，推进至报告审核环节；3\. 接收审核人退回的报告，按要求修改后重新提交；4\. 不可修改已校核的现场记录，若发现现场记录问题，需反馈至校核员/管理员。|文件库查看（本项目现场记录、本人编制的报告）、报告编制、签字确认、报告修改、案件查看（本项目需编制报告的案件）|仅查看本项目的现场记录，查看、操作本人编制的报告，不可查看其他编制人的未完成报告|
|report\_auditor|审核人|1\. 编制人签字后，对报告的规范性、准确性、完整性进行审核；2\. 审核通过后签字确认，推进至授权签发环节；3\. 审核不通过时，明确退回原因（区分报告编制问题、现场记录问题），退回至对应环节；4\. 可查看现场记录，用于核对报告数据，但不可修改现场记录和报告内容。|文件库查看（本项目所有现场记录、所有编制完成的报告）、报告审核、签字确认、退回操作、案件查看（本项目所有待审核/已审核案件）|查看本项目所有现场记录、所有报告，可退回至编制人或校核员环节，不可操作其他项目的审核工作|
|authorized\_signatory|授权签字人|1\. 对审核通过的报告进行终审，确认无误后签字签发；2\. 签发时写入签发日期（同步至InspectionCaseWorkflowState\.issue\_date与Report\.issued\_at）；3\. 终审不通过时，明确退回原因，退回至审核人或编制人环节；4\. 拥有本项目所有案件的查看权限，可监督全流程，但不可直接修改任何环节内容。|文件库查看（本项目所有现场记录、报告）、终审签字、签发操作、退回操作、案件查看（本项目所有案件，含已完成）|查看本项目所有数据，仅可对审核通过的报告进行签发操作，不可越权干预前端环节|

### 2\.2 角色优化补充说明

1. **权限细化**：取消“默认权限与app\_user一致”的模糊定义，为每个角色分配精准的基础权限，避免权限冗余（如检测员不可查看报告编制相关内容）；

2. **数据权限控制**：新增数据权限列，明确每个角色仅能操作本项目、本人相关的数据，符合企业“项目隔离、岗位隔离”的管理要求，防止数据泄露；

3. **角色互斥规则**：补充企业级角色互斥要求——同一用户在同一项目中，不可同时担任两类及以上检测业务角色（如不可同时为检测员和校核员），避免自我操作、自我审核的风险；super\_admin、admin可跨项目查看数据，但不可直接参与检测业务操作（需单独分配业务角色方可操作）；

4. **角色种子数据**：优化种子数据配置，新增角色时自动关联基础权限，减少管理员手动配置成本；同时记录角色创建人、创建时间，便于权限追溯；

5. **APP\_SIDE\_ROLE\_CODES优化**：集合APP\_SIDE\_ROLE\_CODES（field\_inspector、site\_reviewer、report\_author、report\_auditor、authorized\_signatory、app\_user），补充权限校验逻辑——仅该集合内的角色可参与任务分配、调用检测API，非集合内角色（如template\_tester）不可参与业务操作。

### 2\.3 权限维护优化

保留“角色管理 → 编辑角色”的权限细调入口，优化以下两点：

- 新增权限分类：将权限分为“基础操作权限”“数据查看权限”“流程操作权限”三类，管理员可按分类细调，避免权限配置混乱；

- 权限变更记录：新增权限变更日志，记录管理员对角色权限的修改操作（修改人、修改时间、修改内容），便于企业权限审计。

## 三、项目流程成员优化（LibraryProjectWorkflowMember）

基于原有“项目级流程成员”定义，补充企业级管控规则、维护权限、批量操作功能，确保项目成员分配规范、可管控。

### 3\.1 核心优化内容

1. **约束强化**：保留“\(project, user\)唯一”约束，新增补充约束——同一用户在同一项目仅能分配一个流程岗位（五选一）；同一项目中，每个流程岗位至少分配1名用户（避免某环节无人负责，导致流程停滞）；

2. **维护权限细化**：明确“分配文件库任务”权限的分级——admin、super\_admin可维护所有项目的流程成员；项目负责人（新增角色，可在项目创建时指定）仅可维护本项目的流程成员；普通管理员无成员维护权限，避免越权分配；

3. **维护入口优化**：在“项目管理”页“项目检测流程”卡片中，补充以下功能：
        

    - 批量添加/移除成员：支持批量选择用户、分配岗位，减少管理员重复操作；

    - 成员变更记录：记录成员添加/移除的操作人、操作时间、变更前岗位、变更后岗位，便于流程追溯；

    - 岗位空缺提醒：若某流程岗位无成员分配，显示红色提醒，督促管理员及时补充；

    - 成员权限预览：点击成员可预览其对应岗位的权限，便于管理员核对分配是否正确。

4. **Django Admin维护优化**：在Django Admin的LibraryProjectWorkflowMember维护页面，新增“项目筛选”“岗位筛选”功能，支持快速查询；同时添加数据校验，避免违反约束条件的操作（如重复分配、岗位空缺）。

### 3\.2 API鉴权优化（企业级安全管控）

原有鉴权逻辑基础上，补充双重校验，确保操作合规：

1. 基础校验：用户全局Role需在APP\_SIDE\_ROLE\_CODES集合内；

2. 岗位校验：用户需在当前项目被指派为对应workflow\_role；

3. 环节校验：用户当前操作的案件workflow\_state\.stage，必须与该岗位可操作的环节一致；

4. 新增校验：操作人需为当前环节的指定负责人（如报告审核环节，仅本项目的report\_auditor可操作），避免跨岗位操作；

5. 鉴权日志：新增API鉴权日志，记录用户操作、鉴权结果、操作时间，便于安全审计和问题排查。

## 四、案件环节优化（InspectionCaseWorkflowState）

保留与InspectionCase一对一的关联关系，优化字段定义、状态流转规则、数据回填逻辑，确保案件环节清晰、可追溯，贴合企业级案件管理需求。

### 4\.1 字段优化（补充企业级追溯需求）

|字段|说明（优化后）|企业级补充要求|
|---|---|---|
|stage|当前环节，取值见模型STAGE\_\*（顺序：现场填写 → 现场校核 → 报告编制 → 报告审核 → 授权签发 → 已签发），不可跳环节流转|新增环节流转记录，记录每个环节的进入时间、离开时间、操作人，形成完整的环节流转轨迹|
|return\_reason|最近一次退回说明，需明确退回原因（选项\+自定义输入，避免模糊表述）|退回原因需分类（如现场记录错误、报告编制错误、数据不一致），便于后续统计分析问题类型|
|issue\_date|签发日期（授权签字人签发时由服务写入，默认当天，不可手动修改）|签发日期需与Report\.issued\_at严格对齐，同步写入时间戳，避免时间不一致；新增签发人字段，关联授权签字人信息|
|updated\_by / updated\_at|最后操作者与时间|补充操作类型字段（如“推进环节”“退回环节”“签发报告”），明确操作行为|
|新增：stage\_operator|当前环节负责人，关联LibraryProjectWorkflowMember中的用户|便于明确各环节责任主体，避免无人负责的情况，同时支持任务提醒|
|新增：return\_count|案件被退回的总次数|用于统计各环节退回率，优化流程、提升工作质量|

### 4\.2 环节流转优化

1. **新建案件**：由信号自动创建状态，默认SITE\_FILL（现场填写），同时自动关联本项目的field\_inspector作为stage\_operator，发送任务提醒（如系统消息、邮件）；

2. **历史案件回填**：在迁移0029\_workflow\_roles\_and\_case\_workflow中，补充回填stage\_operator、return\_count、环节流转记录，确保历史数据完整可追溯；

3. **环节流转约束**：严格按照“现场填写→现场校核→报告编制→报告审核→授权签发→已签发”的顺序流转，不可跳环节（如检测员不可直接将案件推进至报告审核环节）；已签发环节不可退回，确保报告的严肃性；

4. **任务提醒**：新增环节任务提醒功能，当案件流转至某环节时，自动向该环节的stage\_operator发送提醒，避免任务遗漏（提醒方式可配置：系统消息、邮件、APP推送）。

## 五、环节推进与「退回上一环节」优化（workflow\_service）

基于原有workflow\_service模块，优化函数逻辑、补充校验规则、新增异常处理，确保流程操作合规、可追溯，适配企业级流程管控需求。

### 5\.1 原有函数优化

1. **transition\_case\_stage\(case, new\_stage, user=\.\.\., return\_reason=\.\.\., issue\_date=\.\.\.\)**

    - 新增校验：校验user是否为当前项目对应岗位的成员，且new\_stage是否为当前环节的下一个环节（不可跳环节）；

    - 补充操作记录：调用该函数时，自动记录环节流转记录（当前环节、新环节、操作人、操作时间、备注）；

    - 异常处理：若校验失败，抛出明确的异常信息（如“无权限操作该环节”“不可跳环节流转”），便于API/App捕获并提示用户；

    - 签发同步：当new\_stage为ISSUED（授权签发）时，自动调用set\_issue\_date\_from\_signatory函数，同步写入issue\_date和Report\.issued\_at。

2. **reject\_case\_to\_previous\_stage\(case, user=\.\.\., reason=\.\.\.\)**

    - 细化退回规则：明确各环节的退回映射（如授权签发环节退回至报告审核环节，报告审核环节可退回至报告编制环节或现场校核环节，需根据退回原因选择）；

    - 校验优化：校验user是否有权限退回（仅当前环节的负责人可发起退回）；reason需符合规范（选择分类\+自定义说明），否则无法提交；

    - 数据更新：退回时，自动更新return\_reason、return\_count、updated\_by、updated\_at，同时记录退回记录（退回人、退回时间、退回原因、退回至哪个环节）；

    - 提醒补充：退回后，自动向被退回环节的stage\_operator发送提醒，告知退回原因和修改要求。

3. **set\_issue\_date\_from\_signatory\(case, user=\.\.\.\)**

    - 权限校验：仅authorized\_signatory角色可调用该函数，且user需为当前项目的授权签字人；

    - 时间同步：写入issue\_date时，同步更新Report\.issued\_at，确保两个字段时间一致；同时记录签发人（user）信息，便于追溯；

    - 状态锁定：签发后，案件状态锁定为“已签发”，不可再进行任何环节操作（包括退回），确保报告的法律效力。

### 5\.2 新增企业级函数（补充流程管控）

1. **get\_case\_workflow\_trace\(case\)**：获取案件的完整流程流转轨迹，返回所有环节的操作人、操作时间、环节状态、退回原因等信息，用于企业流程审计和问题追溯；

2. **batch\_transition\_case\_stage\(cases, new\_stage, user=\.\.\.\)**：支持批量推进多个案件的环节（需用户有权限操作所有案件的对应环节），提升管理员工作效率；

3. **reset\_case\_stage\(case, target\_stage, user=\.\.\., reason=\.\.\.\)**：仅super\_admin、admin可调用，用于特殊场景下（如数据错误）重置案件环节至指定阶段，需填写详细原因并记录操作日志，避免滥用。

### 5\.3 后续API/App衔接要求（优化后）

在检测提交、现场记录上传、报告签发等API/App操作中，需严格接入上述函数，并补充以下衔接要点：

1. 所有流程操作（推进、退回、签发）均需调用workflow\_service中的对应函数，不可直接修改InspectionCaseWorkflowState字段，确保流程规则统一；

2. API/App需捕获函数抛出的异常，转化为用户可理解的提示（如“您无权限签发报告”“请填写完整的退回原因”）；

3. 现场记录上传、报告提交时，需校验用户签字的真实性（如电子签字校验），避免代签、伪造签字；

4. 签发成功后，同步更新Report\.status为“已签发”，并向相关人员（项目负责人、检测员、编制人）发送签发通知；

5. API/App需展示案件的完整流程轨迹（调用get\_case\_workflow\_trace函数），便于各岗位查看案件进度和历史操作。

## 六、项目管理页「可视化」优化

在原有可视化基础上，补充企业级管理所需的统计、筛选、预警功能，提升管理员对项目流程、案件进度的管控效率。

### 6\.1 原有可视化优化

1. **流程步骤条**：横向标签与InspectionCaseWorkflowState\.STAGE\_CHOICES顺序一致，补充各环节的完成率、当前待处理案件数量，点击环节可查看该环节的所有案件；

2. **流程成员表**：补充成员的岗位权限预览、负责案件数量，支持按岗位筛选成员，便于管理员快速定位各岗位负责人；

3. **案件当前环节表**：新增筛选功能（按环节、按退回次数、按操作人筛选），补充案件的处理时长（当前环节停留时间），超过规定时长（可配置）的案件标红提醒，避免流程停滞。

### 6\.2 新增企业级可视化功能

1. **流程统计面板**：展示本项目的案件总数、各环节案件数量、退回率、平均处理时长，支持按时间范围筛选（如近7天、近30天），便于管理员掌握项目流程效率；
