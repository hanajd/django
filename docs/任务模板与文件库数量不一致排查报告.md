## 1. 背景与问题描述

用户反馈：

1. **任务模板库**中显示的模板数量（PDF / JSON）与**文件库「模板」页**入库数量不一致；
2. 有用户反映模板**无法保存**、**回档（恢复历史绑定）**异常。

本报告在上一轮已排除 `history/` 干扰后，**仅针对 `current/` 当前文件与任务模板绑定**复核结论，并补充保存/回档机制分析。

## 4. 数量不一致：根因分类

### 4.1 三套统计口径（核心原因）

系统内至少存在**三种不同的计数方式**，直接对比必然不一致：

| 位置 | 统计对象 | 代码/逻辑 |
|------|----------|-----------|
| **任务模板库**「已绑定 N 个模板文件」 | 该任务 M2M 关联的 `category=template` 记录数 | `manage_task.library_files.filter(category=TEMPLATE).count()`（`views.py`） |
| **文件库「模板」页**某任务节点 | 同上，但经权限过滤、`keep_library_files_on_disk` 剔除磁盘缺失记录；多任务共用文件只归入 **code 排序最靠前** 的任务 | `_nest_file_library_by_library_task` + `_annotate_file_library_display` |
| **`_task.json` manifest `files.current`** | 扫描任务目录 `current/` 下**所有物理文件**（含未绑定孤儿） | `_write_manifest_for_task` 目录遍历（`template_storage_service.py`） |
| **侧栏树节点数字** | 仅 **PDF**，且仅 M2M 绑定且磁盘存在 | `_node_pdf_count` / `_template_pdfs_for_task` |
| **实际检测/导出生效** | **1 PDF + 1 主 JSON** | `get_task_template_pair()` |

**结论**：任务页与文件库任务节点在「当前绑定」层面**口径一致**；若与 manifest 或直接数文件夹内文件对比，会因 manifest 计入孤儿文件而偏大。

### 4.2 当前层任务分类统计（59 个有 manifest 的任务）

| 类型 | 任务数 | 含义 |
|------|--------|------|
| 正常对齐（磁盘 2 个 ≈ M2M 2 个） | **33** | 任务页与文件库应一致 |
| `current/` 磁盘文件 **多于** M2M 绑定 | **13** | 存在「落盘但未绑定」孤儿 |
| M2M 有绑定，文件在**其他任务存储目录** | **6** | 绑定路径与任务目录错位 |
| `current/` 有文件但 **M2M 为 0** | **3** | 保存落盘成功、绑定完全失败 |

`current/` 路径：DB 共 **297** 条模板记录，其中仅 **97** 个文件有任务绑定 → 约 **200** 条为 `current/` 落盘但未绑定。

### 4.3 多任务共用同一文件（次要因素）

- DB 中 **5** 个 `library_file_id` 被多个任务同时 M2M 绑定；
- 文件库展示时每个文件只归入一个任务节点（按 `code` 排序取第一个）；
- **7** 个任务出现「任务页 M2M 计数 > 文件库该节点显示数」。

**不是** JS010 等任务「76 vs 2」类差距的主因。

| `mammography-status-report` | 10 PDF + 1 JSON | 1 + 1 | 同上 |
| `oral-cbct-status-site` | 7 PDF + 1 JSON | 1 + 1 | 多 PDF 孤儿 |
| `oral-cbct-status-report` | 6 PDF + 1 JSON | 1 + 1 | 多 PDF 孤儿 |

## 7. 「模板无法保存」机制分析

### 7.1 保存是两步分离流程

编辑器「保存坐标模板 JSON」调用 `htmlpdf_api_export_json`（`views.py`）：

1. **`save_library_binary_uploads`**：写磁盘（有任务则写入该任务 `current/`），创建 `LibraryFile` 行；**不自动 M2M 绑定**。
2. **`_maybe_rotate_task_json_binding_after_export`** → **`replace_task_template_file_binding`**：将任务主 JSON 绑定轮换为新文件。

任一步成功、另一步失败，即产生用户感知的「保存异常」。

### 7.2 已识别的失败 / 半失败场景

| 场景 | 用户感知 | 技术结果 |
|------|----------|----------|
| 未从「任务模板库」进入编辑器（URL 无 `return_manage_task` / 无 `libraryTaskId`） | 提示「未更新任务绑定」；重进编辑器仍载旧 JSON | 文件可能写入 `_unassigned/current/` 或无法解析任务 |
| 无任务模板维护权限 | `无权维护该任务模板绑定` | 文件已落盘，M2M 未更新 |
| 保存的是「前端规则 JSON」 | 拒绝绑定主模板 | 设计行为，需用「保存坐标模板 JSON」 |
| 存储配额超限 | HTTP 500「模板保存失败」 | `quota_exceeded` |
| 第 1 步成功、第 2 步失败 | 文件库有新文件，任务仍显示旧绑定 | **`current/` 孤儿** |

前端已有半成功提示（`htmlpdf/templates/index.html`）：绑定轮换失败时在 alert 中追加「注意：未更新任务绑定 — …」。

### 7.3 孤儿文件实证：`drct`

`drct` 任务 `current/` 下 5 个模板文件，`library_filetask` 链接均为 **0**：

| library_file_id | 类型 | 创建时间 |
|-----------------|------|----------|
| 1878 | PDF | 2026-06-02 |
| 2215 | JSON | 2026-06-08 |
| 2216 | PDF | 2026-06-09 |
| 2217 | PDF | 2026-06-09 |
| 2218 | JSON | 2026-06-09 |

符合「落盘成功、绑定轮换未执行或失败」模式。

### 7.4 JSON 轮换时的额外清扫行为

`replace_task_template_file_binding` 在替换 JSON 时，除 M2M 已绑定旧 JSON 外，还会扫描 `list_task_storage_current_json_files`（**current 目录下所有主 JSON，含未绑定**）一并轮换进 `history/`。  
若此前已有保存半失败留下的孤儿，下次成功保存会突然多出一批历史记录。

## 8. 「回档（恢复历史绑定）」机制分析

### 8.1 入口与流程

- 任务模板库页 → `action=restore_task_template_history`（`views.py`）
- 调用 `restore_task_template_from_history`（`library_task_template_binding_service.py`）
- 内部仍走 `replace_task_template_file_binding`，将历史文件移回 `current/` 并更新 M2M

### 8.2 数据层面可恢复性

| 检查项 | 结果 |
|--------|------|
| `LibraryTaskTemplateBindingHistory` 总记录 | **444** |
| 指向已软删 `LibraryFile` 的记录 | **0** |
| DB 行存在但磁盘文件缺失 | **0** |

从数据完整性看，回档**不应**因「文件不存在」而批量失败。

### 8.3 用户感知异常的可能原因

| 原因 | 说明 |
|------|------|
| **恢复后编辑器未刷新** | 回档仅更新绑定并 redirect 回任务页；编辑器默认 JSON 由 `pick_task_primary_json_template` 选取，不自动重载 |
| **历史记录污染** | 恢复 JS010 下混入的 JS008 牙片 JSON 会把错误类型模板绑回当前任务 |
| **多任务共用文件** | 回档执行 `relocate` 时可能改变物理路径；旧文件若仍绑定其他任务则**不会**移入 `history`（`if not old.library_tasks.exists()` 才归档） |
| **绑定与目录错位** | 全景/CBCT 等任务绑定文件本就不在本任务目录，回档后 manifest / 文件库 / 任务页更易不一致 |

### 8.4 JS010 绑定历史

任务 25 有 **77** 条 `LibraryTaskTemplateBindingHistory`（审计用，**不等于**当前绑定数）。最近几条均为 JS010 自身 JSON 轮换记录，磁盘均可访问。

## 11. 建议修复方向（待评估，尚未实施）

以下仅供决策参考，**本次未改代码**：

### 11.1 统计口径统一

- 任务页计数与列表均经 `keep_library_files_on_disk` 过滤后再显示；或
- manifest `current` 仅列出 M2M 绑定文件，而非目录全扫描；或
- 文档/UI 明确标注「已绑定」与「目录内文件（含归档草稿）」区别。

### 11.2 保存原子性

- 绑定轮换失败时回滚刚写入的 `LibraryFile` / 磁盘文件，或整体返回失败而非半成功；
- 保存成功时强制校验 `libraryTaskId` 已解析且用户有编辑权限。

### 11.3 数据清理（需单独方案）

- 清理 `current/` 下无 M2M 的孤儿模板（尤其 dr-6、drct 等）；
- 修正绑定路径与任务存储目录不一致的记录；
- 清理或迁移 JS010 history 中 JS008 污染条目。

### 11.4 回档体验

- 恢复成功后提示重新打开编辑器，或 API 返回新 `default_json_template_id`；
- 恢复前校验 `original_name` / `templateId` 与任务类型一致，拦截明显污染记录。

### 11.5 已有修复命令（运维向）

代码库中已有（未在本报告执行）：

- `repair_task_template_library`
- `fix_repaired_task_templates`
