# 项目潜在风险与优化建议

> **文档性质：** 代码、模型、路由、现有文档的静态审查记录。  
> **审查范围：** 项目任务、检测 API、检测提交、现场记录 / 报告 PDF、文件库、流程枢纽、权限、OCR、部署配置。  
> **当前状态：** 本文只记录风险与建议，不代表相关问题已经修复。上线前应结合测试数据和真实部署环境逐项验证。

## 1. 审查结论

项目目前的核心业务链路是：

```text
项目 / 委托
  → 任务模板与任务分配
  → 项目内 taskNo
  → InspectionCase
  → InspectionSubmission
  → 提交 JSON、照片、签名、附件
  → 现场记录 PDF
  → 报告 PDF
  → 审核 / 签发 / 下载
```

当前最需要关注的不是单个页面功能，而是以下系统性问题：

1. **项目内编号与数据库全局唯一约束存在冲突，可能造成跨项目串案。**
2. **Web、v1、v2、流程枢纽使用的权限和项目集合不完全一致。**
3. **数据库事务与文件系统写入不是同一个事务，可能产生部分成功或脏数据。**
4. **报告导出、OCR 和异步任务的可靠性与幂等性不足。**
5. **生产配置仍保留开发默认值，需要增加强制校验。**
6. **主业务链路的端到端测试覆盖不足。**

其中，第一项属于最高优先级数据风险。

---

## 2. 风险等级定义

| 等级 | 含义 | 处理要求 |
|---|---|---|
| P0 | 可能导致数据串案、数据丢失、越权或生产不可用 | 上线前必须处理或有明确隔离方案 |
| P1 | 高概率导致功能异常、流程中断或数据不一致 | 应尽快处理并补回归测试 |
| P2 | 中低概率问题、运维隐患或用户理解偏差 | 纳入后续迭代和监控 |

# 3. P0：必须优先处理的问题

## 3.1 `taskNo` 的项目内语义与全局唯一约束冲突

### 当前情况

项目任务号由项目内任务顺序生成，例如：

```text
项目 A：01、02
项目 B：01、02
```

任务号生成逻辑在：

- `apps/api/inspection_views.py`
- `_build_project_task_no()`

但 `InspectionSubmission.task_no` 使用了全局唯一约束，模型位于：

- `apps/core/models.py`
- `InspectionSubmission`

### 风险

当两个项目都存在 `taskNo=01` 时，可能出现：

- 项目 B 的提交覆盖项目 A 的提交
- 更新项目 B 时删除项目 A 的提交记录
- 草稿、状态、仪器和签名串到其他项目
- 报告生成时使用错误的数据源
- 历史记录列表出现错误数据

提交逻辑中还存在按照全局 `task_no` 删除其他记录的代码，这会放大问题。

### 优化建议

不能再以单独的 `task_no` 作为提交记录的唯一标识。建议改为：

```text
project_id + task_no
```

或者：

```text
case_id + task_no
```

数据库层建议使用联合唯一约束：

```python
UniqueConstraint(
    fields=["project", "task_no"],
    name="uniq_submission_project_task_no",
)
```

同时全面排查以下查询：

```python
filter(task_no=...)
filter(task_no__in=...)
```

凡是项目内任务号查询，都必须附带 `project` 或 `case` 条件。

---

## 3.2 `InspectionCase.case_no` 可能跨项目复用

### 当前情况

`InspectionCase.case_no` 当前为全局唯一，但自动创建案件时使用项目内的 `taskNo` 作为 `case_no`。

创建案件的逻辑会先按 `case_no` 查找；如果当前项目没有找到，还会回退到同编号的其他案件。

### 风险

例如：

```text
项目 A / case_no=01
项目 B / taskNo=01
```

项目 B 创建案件时可能复用项目 A 的 `case_no=01` 案件，后果包括：

- 项目 B 的检测数据写入项目 A
- 项目 B 的医院和设备关联到项目 A
- 文件库项目关联与案件关联矛盾
- 用户被错误地拒绝访问，或者看到其他项目数据
- 报告生成使用错误的案件上下文

### 优化建议

二选一：

#### 方案一：案件编号全局生成

例如：

```text
260001-01
260002-01
```

保留 `case_no` 全局唯一。

#### 方案二：案件编号改为项目内唯一

保留展示编号 `01`，取消全局唯一，增加：

```python
UniqueConstraint(
    fields=["library_project", "case_no"],
    name="uniq_case_project_case_no",
)
```

所有查询必须改成：

```python
InspectionCase.objects.filter(
    library_project=project,
    case_no=task_no,
)
```

不能继续只按 `case_no` 查询。

---

## 3.3 项目、任务、案件的主键语义需要重新明确

当前系统同时使用：

- 项目编码 `project.code`
- 项目主键 `project.pk`
- 项目公开编号 `project_public_id`
- 项目内任务号 `taskNo`
- 分配任务编号 `ASG-*`
- 案件编号 `case_no`
- 任务模板编码 `LibraryTask.code`

如果这些编号在 API、文件名、数据库和页面中混用，后续很容易出现关联错误。

建议明确以下规则：

| 对象 | 推荐唯一标识 | 是否对外展示 |
|---|---|---|
| 项目 | `project.pk` 或稳定 `project.code` | 可展示项目编码 |
| 项目内任务 | `project_id + library_task_id` | 展示 `taskNo` |
| 案件 | `case.pk` | 可展示业务案件编号 |
| 提交 | `submission.pk` 或 `case_id + version` | 不建议只展示 taskNo |
| 报告 | `case_id + report_task_id + version` | 展示报告编号和版本 |
| 文件 | `LibraryFile.pk` | 对外使用下载地址 |

展示名称可以使用 `taskNo`，但业务关联不能只依赖 `taskNo`。

# 4. P1：数据一致性与业务链路风险

## 4.1 数据库事务与文件系统写入不一致

检测提交会依次写入：

- `InspectionSubmission`
- 仪器记录
- 照片
- 二进制附件
- 提交 JSON
- 签名文件
- 现场记录 PDF
- 报告 PDF
- 文件库关联

数据库事务不能回滚已经写入磁盘的文件。因此中途失败后可能出现：

```text
数据库有记录，磁盘没有文件
磁盘有文件，数据库没有记录
PDF 已生成但没有正确关联任务
JSON、PDF、照片不属于同一个批次
```

### 优化建议

采用临时文件 + 原子移动模式：

1. 所有文件先写临时目录。
2. 校验文件大小、哈希和格式。
3. 数据库事务提交。
4. 事务成功后将文件原子移动到正式目录。
5. 失败时清理临时目录。
6. 定时扫描孤立文件和缺失文件。

建议文件记录增加：

```text
project_id
case_id
library_task_id
submission_id
batch_id
generation_id
source_type
content_sha256
```

---

## 4.2 提交成功与 PDF 生成成功没有完全分离

当前提交接口可能返回提交成功，但 `pdfGeneration` 中某个 PDF 生成失败。

这在技术上可以理解为“数据提交成功、异步产物失败”，但如果前端只根据 HTTP 200 判断，就会造成误解：

```text
用户认为报告已经生成
实际只有 JSON
```

### 优化建议

API 响应应明确区分：

```json
{
  "submission": "success",
  "siteRecordPdf": "success",
  "reportPdf": "pending",
  "message": "检测已提交，报告尚未生成"
}
```

并将生成状态持久化，而不是只放在本次响应中。

---

## 4.3 默认提交只生成当前任务 PDF

当前 `_pick_submit_generation_tasks()` 的设计是：

- 如果提交的是现场记录任务，默认生成现场记录 PDF
- 不会自动扫描项目内所有任务生成报告
- 报告通常需要手动导出或单独触发

这属于当前设计，但非常容易被理解为系统故障。

### 优化建议

如果保留当前设计：

- API 返回对应报告任务信息
- 明确返回 `reportPending=true`
- 页面提示“现场记录已生成，报告需要进入报告流程导出”
- 流程枢纽显示下一步入口

如果产品要求“提交后自动出报告”，则应设计明确的后台生成任务，而不是简单扫描全部项目任务。

---

## 4.4 报告任务唯一回退可能掩盖配置错误

当 taskNo 无法解析或现场任务没有正确关联报告任务时，系统可能回退到“项目内唯一报告任务”。

风险是：

- 错误模板仍然能够生成报告
- 用户看不到真正的任务链配置问题
- 设备类型或检测类型不一致时，报告内容可能填入错误模板

### 优化建议

生产环境默认要求严格匹配：

```text
现场任务必须属于报告任务 report_source_tasks
设备类型必须一致
检测类型必须一致
项目必须包含完整任务链
```

唯一报告回退只允许旧版兼容接口使用，并在日志中记录警告。

---

## 4.5 多份 JSON 合并规则复杂，存在字段串位风险

当前不同字段使用不同合并策略：

- `dynamicData`：先出现的键优先
- `testResult`：后面的内容覆盖前面的内容
- `reportInfo/hospitalInfo/equipmentInfo`：前一份非空优先
- `signatures/conclusion`：后面的覆盖前面的

多设备、多现场任务、多模板时，容易出现：

- 不同模板的 `f1`、`f2` 字段含义不同
- 第二台设备覆盖第一台设备的数据
- 勾选顺序影响最终报告
- 空值和缺失值处理不一致

### 优化建议

动态字段使用命名空间：

```text
task:<task_id>:equipment:<equipment_id>:field:<field_id>
```

合并时以：

```text
任务 + 设备 + 字段
```

作为唯一键。文件勾选顺序只能影响展示顺序，不应改变业务数据归属。

---

## 4.6 重复导出报告不是幂等操作

重复点击导出可能会创建多个报告文件记录。后续如果只按创建时间取“最新报告”，可能出现：

- 文件库产生大量重复 PDF
- 预览或下载旧版本
- 签名叠加到错误报告
- 合并报告选择重复文件

### 优化建议

报告导出应区分：

```text
当前草稿
历史版本
审核版本
签发快照
```

建议规则：

- 草稿阶段重复导出覆盖当前草稿
- 审核阶段生成新版本并标记当前版本
- 签发后生成不可修改快照
- 报告表增加版本号、生成时间、生成来源和当前标记

# 5. P1：权限与数据范围风险

## 5.1 项目级权限和任务级权限需要严格区分

部分逻辑先校验具体任务分配，后续又只判断用户是否被分配到该项目。

可能出现：

```text
用户被分配项目 A 的任务 01
用户没有被分配任务 02
但任务 02 的 API 仅凭项目级分配被放行
```

### 优化建议

任务级操作必须统一使用：

```python
LibraryTaskAssignment.objects.filter(
    project=project,
    library_task=library_task,
    assignee=user,
).exists()
```

项目级权限只能用于项目概览，不能替代具体任务权限。

---

## 5.2 任务列表中的空集合语义不明确

当前逻辑中，`allowed_ids` 为空时可能退回项目全部任务：

```python
all_ordered if allowed_ids is empty else filtered_tasks
```

但空集合可能有两种含义：

1. 当前用户没有任务限制，允许看全部。
2. 当前用户没有任何允许任务。

如果不区分，可能造成任务越权展示。

### 优化建议

使用不同语义：

```python
None  # 不限制
set()  # 没有可访问任务
```

并在权限服务中统一定义。

---

## 5.3 签名上传应绑定流程岗位和当前阶段

签名接口支持：

```text
author
reviewer
approver
```

不能只校验用户能否访问项目，还应校验：

- 用户是否为该项目对应流程成员
- 用户是否拥有对应岗位
- 当前流程阶段是否允许签名
- 报告是否已经进入对应阶段
- 已签发报告是否禁止修改

建议形成如下规则：

| 签名 | 推荐岗位 | 推荐阶段 |
|---|---|---|
| author | 编制人 / 检测员 | 报告编制 |
| reviewer | 校核员 / 审核人 | 报告审核 |
| approver | 授权签字人 | 报告签发 |

---

## 5.4 多套权限集合导致页面与 API 结果不一致

项目中同时存在：

- 全局角色权限
- 项目负责人
- 任务分配
- 流程成员
- “仅本人数据”
- 项目编辑撤销
- 委托统筹权限
- 管理员权限

如果不同模块各自拼接条件，就会出现：

```text
页面能看到，API 不能操作
API 能访问，页面没有入口
能看项目，不能看具体任务
能看文件，不能下载文件
能进入报告，不能签名
```

### 优化建议

建立统一授权服务，至少提供：

```python
can_view_project(user, project)
can_view_task(user, project, task)
can_view_case(user, case)
can_edit_submission(user, case)
can_export_site_record(user, case)
can_export_report(user, case)
can_upload_signature(user, case, role)
can_issue_report(user, case)
```

Web、API v1、API v2、流程枢纽统一调用。

# 6. P1：异步任务、OCR 与资源风险

## 6.1 OCR 使用 daemon 线程，不适合生产

当前 OCR 任务通过后台 daemon 线程执行。进程、worker 或容器重启时，任务可能直接消失。

可能出现：

- 任务永远停在 `pending`
- 任务停在 `running` 而没有结果
- Gunicorn worker 重启后无法恢复
- 多个 OCR 同时运行导致 GPU OOM
- 失败没有重试

### 优化建议

优先使用：

- Celery + Redis / RabbitMQ
- RQ
- 独立任务 worker

如果暂时不迁移队列，至少增加：

```text
任务锁
超时时间
重试次数
worker 标识
开始 / 结束时间
超时任务恢复
```

---

## 6.2 外部依赖失败需要统一降级语义

项目依赖：

- MinerU
- Ollama
- Node / MathJax
- LaTeX
- 中文字体
- PyMuPDF
- pdf2image

不同环节失败时，应明确区分：

```text
核心业务不可用
仅 OCR 不可用
仅公式叠印不可用
仅评价报告书不可用
仅放射防护附加表不可用
```

不能把可选能力失败统一表现成“提交失败”，也不能把核心能力失败伪装成成功。

### 优化建议

增加启动检查和能力状态接口：

```text
GET /health/
GET /health/dependencies/
```

返回：

```text
database
media_storage
font
mineru
ollama
latex
node
```

每个能力独立报告状态。

# 7. P1：文件库、流程枢纽与页面一致性

## 7.1 多个页面使用不同项目集合

当前页面的数据契约不同：

| 页面 | 主要数据来源 |
|---|---|
| 项目工作台 | 项目配置、设备、任务 |
| 委托管理 | 项目权限、设备和流程进度 |
| 原始记录 | 已生成的现场记录文件 |
| 报告编制 | 报告阶段和待办条件 |
| 报告预览 | 已存在的报告 PDF |

因此以下现象可能是当前设计，而不是数据库丢数据：

```text
工作台有项目，原始记录没有
委托管理有项目，报告编制没有
医院信息有项目，流程枢纽没有
```

### 优化建议

页面应明确显示筛选契约，例如：

```text
此页面仅显示已有现场记录 PDF 的委托
此页面仅显示处于报告编制阶段的委托
此页面仅显示已经生成报告的委托
```

同时提供“显示全部”和“隐藏原因”。

---

## 7.2 流程枢纽存在项目数量截断

流程枢纽默认只取有限数量的项目。项目量增加后，可能出现：

- 老项目查不到
- 搜索查不到真实存在的项目
- 用户误以为项目被删除

### 优化建议

改为：

```text
先执行权限过滤
再执行关键字过滤
再排序
最后分页
```

不要先取前 120 条再进行页面搜索。

页面应显示：

```text
第 1～50 条，共 326 条
```

---

## 7.3 医院根、院区、科室挂载查询不一致

项目可以挂载到医院、院区或科室，但部分医院关联查询只按医院根节点精确匹配。

可能出现：

```text
工作台能看到
委托管理能看到
流程枢纽能看到
医院信息页关联项目看不到
```

### 优化建议

医院维度统一按组织子树查询：

```text
医院根
  ├── 院区
  │     └── 科室
```

医院关联项目应包含整棵子树，而不是只查询 `commission_org_id=医院根`。

# 8. P1：生产配置与部署风险

## 8.1 生产默认配置过于宽松

当前配置仍包含开发默认值：

```text
DEBUG=True
ALLOWED_HOSTS=['*']
默认 insecure SECRET_KEY
```

如果部署时漏掉环境变量，会造成：

- 错误页泄露调试信息和本地路径
- Host 头校验失效
- 默认密钥可被预测
- 生产问题不容易被发现

### 优化建议

生产启动时强制检查：

```text
DEBUG 必须为 False
SECRET_KEY 不能是默认值
ALLOWED_HOSTS 不能为 *
正式环境必须设置 HTTPS 相关配置
```

建议将以下配置全部改为环境变量：

```text
DEBUG
ALLOWED_HOSTS
CORS_ALLOWED_ORIGINS
DATABASE_URL 或数据库参数
MEDIA_ROOT
STATIC_ROOT
```

---

## 8.2 CORS 文档与实际配置可能不一致

文档说明生产可以配置 CORS，但当前设置中主要是 localhost 来源。

可能导致：

- 外部前端部署后请求失败
- 部署人员误以为环境变量已经生效
- `CORS_ALLOW_CREDENTIALS=True` 与来源配置不匹配

### 优化建议

从环境变量读取逗号分隔的来源列表：

```text
CORS_ALLOWED_ORIGINS=https://example.com,https://app.example.com
```

生产环境不要同时使用：

```text
允许任意来源 + 允许凭据
```

---

## 8.3 SQLite 在并发写入场景可能成为瓶颈

当前默认数据库为 SQLite。低并发演示没有问题，但多人同时提交、OCR、PDF 生成和自动备份时可能出现：

- `database is locked`
- 请求等待或超时
- 状态更新冲突
- 备份和业务写入互相影响

### 优化建议

- 演示环境可继续使用 SQLite
- 正式多人使用建议迁移 PostgreSQL
- 提前排查 SQLite 特有写法
- 对状态更新增加并发控制
- 不要在业务高峰执行全量数据库复制备份

---

## 8.4 备份必须包含数据库和媒体文件

只备份 `db.sqlite3` 不足以恢复系统。必须同时备份：

```text
db.sqlite3
media/file_library/
media/f1_eval/
media/evaluation_reports/
用户签名
报告文件
模板文件
运行时配置
字体文件
```

数据库和媒体必须尽量保持同一时间点，否则可能出现数据库记录存在但文件缺失。

建议定期执行恢复演练，而不是只验证备份命令成功。

# 9. P2：维护性和文档问题

## 9.1 文档索引存在失效链接

# 10. 推荐优化路线

## 第一阶段：数据安全和隔离

1. 明确项目、任务、案件、提交、报告的编号语义。
2. 修复 `case_no/task_no` 的全局唯一冲突。
3. 全面排查只按 `task_no` 或 `case_no` 查询的代码。
4. 增加两个项目使用相同 `taskNo` 的隔离测试。
5. 统一任务级权限判断。

## 第二阶段：业务链路可靠性

1. 增加提交、现场记录、报告的独立状态。
2. 增加 PDF 生成失败记录和重试。
3. 改进文件写入和数据库事务的一致性。
4. 实现报告导出的幂等和版本管理。
5. 严格校验报告任务与现场任务的关系。

## 第三阶段：权限和查询统一

1. 建立统一授权服务。
2. 统一 Web、v1、v2、流程枢纽的项目和任务可见范围。
3. 修复医院子树查询。
4. 枢纽改为真正分页。
5. 增加隐藏原因和权限诊断信息。

## 第四阶段：生产化和运维

1. 生产配置改为环境变量。
2. 增加启动配置检查。
3. OCR 改为可靠任务队列或独立 worker。
4. 评估 PostgreSQL。
5. 建立数据库 + media 的联合备份和恢复演练。
6. 增加健康检查和外部依赖检查。

## 第五阶段：持续质量保障

1. 增加业务一致性巡检命令。
2. 增加孤立文件和缺失文件扫描。
3. 增加重复报告检测。
4. 增加 Markdown 文档链接检查。
5. 建立发布前自动化验收清单。

# 12. 最终结论

当前项目短期单项目、低并发运行时，很多问题可能不明显；但随着项目数、设备数、人员数和报告数量增加，最容易暴露的是：

```text
编号冲突
数据串项目
权限判断不一致
文件与数据库不一致
报告重复和版本错乱
OCR 任务丢失
生产配置遗漏
```

最优先的工作顺序应当是：

```text
先修数据隔离
→ 再统一权限
→ 再保证文件和报告链路可靠
→ 再改进异步任务
→ 最后做性能和页面体验优化
```

其中，`InspectionCase.case_no`、`InspectionSubmission.task_no` 与项目内 `taskNo` 的编号设计必须在继续扩展功能前先定下来。否则后续任何页面优化、报告优化或权限补丁，都可能建立在不稳定的数据关联基础上。
