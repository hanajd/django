# 业务线扩展评估（第三版）：医院信息立项 · 业务线预留

> **文档性质**：需求评估与方案草案（**尚未改代码**）  
> **修订日期**：2026-07-17（第三版）  
> **用途**：供产品/业务确认后，再按确认项落地开发  

---

## 0. 本版新增取向

| 项 | 说明 |
|----|------|
| **委托项目建立位置** | 放到 **医院信息管理** 下完成，对应并收敛当前「项目工作台 · 新建项目」与「委托立项」能力 |
| **业务线实现范围** | 后台 **当前只做检测报告线**；**预评价 / 控制效果评价** 先做 **业务线预留**（选型、字段、入口占位），功能后期再完善 |
| **继承第二版** | 销售不进系统；行政录入起点；两部门工作台操作；派单仅本部门；主任可建本部门用户 |

## 1. 修订后的主路径（行政视角）

```
线下签单
  →【医院信息管理】行政录入医院 / 院区 / 科室 / 设备
  →【医院信息管理】建立委托项目（自动编号 + 项目名）
       · 选择业务线：检测报告 | 预评价（预留）| 控制效果评价（预留）
       · 检测线：挂载设备与检测类型（现「委托立项」能力迁入/复用）
  → 提交到对应部门
  →【项目工作台】检测部 / 评价部：派单与后续
```

**项目工作台**不再作为「从零新建委托项目」的主入口（可保留入口但引导去医院信息，或仅管理员兼容）；工作台专注 **派单、仪器、进度、报告环节**。

## 2. 立项能力迁移：医院信息管理 ↔ 项目工作台

### 2.1 现状（拆开的两处）

| 位置 | 现有能力 |
|------|----------|
| **项目工作台 · 新建项目** | 三步向导：委托单位 → 设备与检测类型 → 可选统筹人；生成 `LibraryProject` |
| **项目工作台 · 委托立项** | 在已有项目上继续挂载设备 / 检测类型 / 报告模板 |
| **医院信息管理** | 医院树、设备台账；**尚无**完整建项向导 |

### 2.2 目标归并

| 能力 | 目标归属 | 说明 |
|------|----------|------|
| 录入医院/地址/设备 | 医院信息管理 | 已有，行政主责 |
| **新建委托项目** | **医院信息管理** | 承接工作台「新建项目」向导（或同款 UI 嵌在医院节点下） |
| **挂载设备与检测类型** | **医院信息管理（建项时）+ 必要时工作台补录** | 建项时完成主挂载；检测部后续若需增补，可在工作台「委托立项」保留补录（权限收窄） |
| 人员派单 | 项目工作台 | 仅本部门；主任操作 |
| 进度 / 报告环节 | 项目工作台 | 检测线现有流程；评价线后期 |

### 2.3 交互建议（MVP）

在医院信息管理中，进入某医院（或科室）详情后提供：

1. **「建立委托项目」** 按钮（行政 / 有建项权）  
2. 向导内容 ≈ 现 `project_create_modal`：选范围（默认当前医院树节点）→ 勾选设备与检测类型 → 选业务线 → 自动编号与项目名 → 提交到检测部或评价部  
3. 提交成功后：跳转或深链到 **项目工作台** 对应项目（检测部待派单队列）

工作台顶栏「新建项目」：改为「请到医院信息管理立项」提示，或隐藏（超管可保留兼容）。

## 3. 业务线：检测已实现 · 评价两条预留

### 3.1 三分叉（数据层立刻预留）

建议在 `LibraryProject`（或委托单）增加：

```text
business_line ∈ { inspection, pre_eval, control_effect }
```

| 值 | 名称 | 本期 | 后期 |
|----|------|------|------|
| `inspection` | 检测报告 | **完整可用**（现有现场→签发，再加归档） | 持续优化 |
| `pre_eval` | 预评价报告 | **仅预留**：可选、落库、工作台占位 | 评价状态机、产物、待办 |
| `control_effect` | 控制效果评价 | **仅预留**：可选、落库、占位；嵌套检测接口预留 | 子项目派单 + 评价流程 |

### 3.2 「预留」具体指什么（避免空壳误用）

| 层 | 预留内容 | 禁止/降级 |
|----|----------|-----------|
| **建项 UI** | 业务线下拉三选一；选评价线时提示「功能开发中，仅登记意向」或仍允许建项但标记 `line_status=reserved` | 不进入虚假的评价编制流程 |
| **数据** | `business_line` 必填；评价线项目可建，便于后期迁移 | 不伪造已完成评价报告 |
| **项目工作台** | 评价部队列可见「预评价 / 控制效果」卡片；详情页展示 **「评价流程即将上线」** 占位 | 不开放未实现的评审会/报送按钮（或灰显） |
| **派单** | 评价线项目：评价主任可先派本部门人（可选）；或本期评价线 **仅登记不派单** | 不要派到检测五岗冒充评价流程 |
| **检测线** | 照常派单与推进 | — |
| **接口/枚举** | 状态机枚举、文件分类、枢纽待办类型 **先定义常量与空分支** | 分支内 `NotImplemented` / 友好提示 |

### 3.3 控制效果「检测派单」预留

数据上预留：

- `parent_project_id`（子检测项目挂评价主项目）  
- 或 `needs_inspection_dispatch` 标记  

本期可不生成子项目；UI 上灰显「发起检测派单」。后期评价线完善时再接通。

### 3.4 与「当前只做检测」的产品表述

> 医院信息管理可登记三类业务意向；**流程与报告能力本期仅打通检测报告**。预评价、控制效果评价项目可先建档排队，功能上线后在同一项目上续作，避免后期再拆单。

若业务担心误用：建项时评价线改为「仅管理员可建」或「仅保存草稿意向单」——请在 §8 确认。

## 5. 检测线本期仍要做的增强（在预留之外）

即使评价线只预留，检测线建议同期完成或紧随：

1. 医院信息管理承接建项（含设备挂载）  
2. 行政角色 + 自动编号/项目名  
3. 部门字段 + 派单本部门过滤  
4. 检测部主任角色与工作台队列  
5. （可选同期）检测线 **归档** 状态  

评价部主任角色与评价队列占位：可与预留一起做，避免后期再改导航。

## 9. 推荐结论（第三版）

1. **委托项目建立放在医院信息管理**，收敛工作台「新建项目 + 委托立项（主挂载）」能力。  
2. **项目工作台**专注部门内派单与后续；检测线全功能，评价线先占位。  
3. **数据与入口预留** `pre_eval` / `control_effect`，避免后期大搬家；本期不实现评价编制/评审会/报送。  
4. 派单本部门隔离、主任建本部门用户、行政录入起点——与第二版一致，优先落地。

## 11. 第四版补充：行政 / 部门角色拆分规划

> **修订日期**：2026-07-21（已按业务确认修订）  
> **范围**：在第三版主路径上，**另建**行政与检测/评价部门角色；**不改动**现有 `commission_coordinator`（委托统筹）行为。  
> **原则**：防越权；行政管医院侧资料与项目壳、不管流程细节；部门主管管员工；岗位权限按项目挂岗生效；新/旧角色派工池隔离。

### 11.0 已确认结论（2026-07-21）

| # | 议题 | 确认 |
|---|------|------|
| 1 | 医院信息写权限 | **仅行政可写**。行政 / 检测部 / 评价部当前为**平级**；若未来有行政上级，可再开写权，本期不做上级角色。部门主管/员工：只读或不入口。 |
| 2 | 主管与员工 | **部门主管管理本部门员工**（本部门全部，非仅本人创建）。 |
| 3 | 建用户是否绑五岗 | **员工默认不建岗**（组织角色仅为部门员工）。未在项目挂岗前权限低；**仅在对应项目下挂了流程岗后**才具备该岗权限。 |
| 4 | 人员派工 UX | **必须优化**：支持多选员工、按岗批量挂载，降低「一岗一人反复点」成本。 |
| 5 | 行政职责边界 | 行政管**医院信息**，并对医院树下的**设备与项目（建项/资料侧）**有管理权；**不负责**项目内流程派工、环节推进、五岗细节。 |
| 6 | 委托统筹 | **不改**；继续独立运行。行政/检测/评价为**新建角色**，与旧体系并行。 |
| 7 | 新旧隔离 | **主要在人员派工候选人池隔离**：新部门主管派工时，只能选本部门「新员工角色」用户，**不可派到旧的全局五岗角色账号 / 统筹体系账号**。旧统筹派工逻辑保持原样。 |

### 11.1 现状基线（委托统筹，保持不动）

当前 `commission_coordinator` 仍可：医院信息、建项、派五岗、管本人创建的五岗账号、文件库导出等。  
本期**不收缩**其权限；新角色走另一套入口与校验，互不影响。

```text
【旧轨 · 不变】委托统筹：医院 → 建五岗账号 → 工作台建项 → 派工(旧候选人池) → …
【新轨 · 新建】行政建项提交部门 → 部门主管管员工/派工(新候选人池) → 项目挂岗后员工才有流程权
```

### 11.2 新建角色矩阵

| Role.code | 名称 | org_unit | 说明 |
|-----------|------|----------|------|
| `admin_office` | 行政 | `admin_office` | 医院信息写；设备；建项/提交到部门；可管医院下项目壳；**无派工、无环节操作** |
| `dept_director_inspection` | 检测部主管 | `inspection` | 接检测线项目；管本部门员工；人员派工（新池）；补录/进度/导出等 |
| `dept_staff_inspection` | 检测部员工 | `inspection` | 默认低权限；**项目挂岗后**才有对应 workflow 权限 |
| `dept_director_evaluation` | 评价部主管 | `evaluation` | 评价队列（本期占位）；管本部门员工；后期派工 |
| `dept_staff_evaluation` | 评价部员工 | `evaluation` | 默认低权限；后期项目挂岗再生效 |

**不改动的既有角色**：`commission_coordinator`、全局五岗（`field_inspector`…`authorized_signatory`）、系统管理员、模板岗等。

数据层：

- 用户：`org_unit`（结构化）+ 上表组织角色  
- 项目：`business_line`、`owning_org_unit`（接收部门）  
- 项目流程岗：继续用 `LibraryProjectWorkflowMember.workflow_role`；**新轨员工的全局 Role 仍是部门员工，不改成全局五岗**

### 11.3 权限对照（新轨）

| 能力 | 行政 | 检测主管 | 检测员工（未挂岗） | 检测员工（已挂岗） | 评价主管 | 评价员工 |
|------|:----:|:--------:|:------------------:|:------------------:|:--------:|:--------:|
| 医院信息写 | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |
| 医院信息读 | ✅ | 👁 | ❌/👁 | 👁 按项目 | 👁 | ❌/👁 |
| 医院下设备管理 | ✅ | 👁（补录策略可另定） | ❌ | ❌ | 👁 | ❌ |
| 建项 / 提交到部门 | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |
| 医院下项目壳 | ✅ | ✅ 本部门 | 👁 被派项目 | 👁 被派项目 | ✅ 本部门 | 👁 被派 |
| 人员派工 / 任务同步 | ❌ | ✅ 新池+本部门 | ❌ | ❌ | ✅ 新池（后期） | ❌ |
| 流程环节 / App 业务 | ❌ | 👁 管理视角 | ❌ 低权 | ✅ 仅所挂岗 | 占位 | 占位 |
| 用户管理（本部门员工） | ❌ | ✅ | ❌ | ❌ | ✅ | ❌ |
| 文件库导出合并等 | 弱/项目只读 | ✅ 部门侧 | 极弱 | 按挂岗规则 | 占位 | 占位 |

### 11.4 「先员工、后挂岗」权限模型

```text
主管创建用户
  → Role = dept_staff_* ，org_unit = 本部门
  → 此时：几乎无业务权

主管在项目「人员派工」中挂岗（支持多选）
  → LibraryProjectWorkflowMember(project, user, workflow_role=…)
  → 同步 LibraryTaskAssignment（如需要）
  → 此时：仅在该 project 上具备对应 workflow 权限
  → 撤岗后：权限收回
```

鉴权要点（新轨）：

1. 全局 Role 为部门员工 ≠ 自动拥有 App 五岗能力。  
2. 业务 API：查**当前项目**的 `WorkflowMember`，不能只看全局 `Role.code`。  
3. 旧轨用户：全局五岗 + 统筹派工，**继续走原逻辑**。  
4. 用「是否新组织角色 / 是否带 org_unit」分支，避免新旧踩踏。

### 11.5 人员派工：新旧池隔离 + UI 多选

**隔离规则（后端强制）**

| 操作者 | 派工候选人 |
|--------|------------|
| 委托统筹（旧） | **维持现状** |
| 检测/评价主管（新） | 仅同 `org_unit` 且 Role 为本部门员工（新角色）；**排除**全局五岗、`commission_coordinator`、行政、跨部门、系统管理员 |

**UI 优化（与权限同期）**

- **多选员工**，一次挂到同一流程岗（如 3 人同时挂检测员）。  
- 按岗分组展示；减少「每岗每人保存一次」的串行操作。  
- 展示已挂岗状态；支持批量撤岗；可筛「未挂岗员工」。

### 11.6 行政边界

**有权**：医院/院区/科室/设备；建项与业务线；提交到部门；医院维度下的项目壳（编号、名称、所属医院、提交状态等）。  

**无权**：人员派工、流程成员、任务同步 App、案件环节推进/退回/签发；可以只读进度摘要便于对外答复。

### 11.7 主路径（新轨）

```text
线下签单
  →【行政】医院信息（写）+ 设备
  →【行政】建项并提交到检测部 / 评价部
  →【部门主管】本部门队列接单
  →【部门主管】创建本部门员工（不绑五岗）
  →【部门主管】人员派工（多选挂岗）+ 同步任务
  →【已挂岗员工】按岗作业
  →【部门主管】进度 / 导出 /（可选）归档
```

旧轨委托统筹可并行，不强制迁移。

### 11.8 后端强制校验清单

1. 医院信息写：仅 `admin_office`（及系统管理员）；预留行政上级扩展点，本期无该角色。  
2. 建项/提交部门：仅行政（及超管）。
